# Analysis of Engine State Explosion and Precision Limits

This document contains theoretical analysis of the performance boundaries, state explosion issues, and fixed-point precision limitations present in the Pokémon AI Engine. 

## 1. Engine Branching Upper Bound

We evaluated the maximum number of states potentially generated by a single round using two all-adjacent moves (such as `earthquake` and `surf`) under a `setAccuracy(16)` constraint.

> [!WARNING]
> Evaluating multiple instances of multi-target moves under high-accuracy settings produces a catastrophic state combination explosion that quickly scales beyond conventional system memory capabilities.

### Calculation Breakdown (2v2 Scenario)
When Pokemon A-0 and A-1 tie in speed:
1. **Turn Permutations:** A speed tie generates **2 branches** for the initial execution order priority.
2. **Hit Splits:** Spread moves in 2v2 hit 3 targets (1 ally, 2 enemies). The critical hit check rolls independently per target (**2 outcomes**).
3. **Damage Splits:** Using `setAccuracy(16)`, the damage rolls map to **16 outcomes**. 
4. **Per Target Branches:** Each independent target incurs $2 \times 16 =$ **32 branches**.

Total states generated per move: $32^3 =$ **32,768 states**

Assuming both moves execute on surviving targets, the resulting cartesian product is:
`2 (permutations) * 32,768 (move 1) * 32,768 (move 2)` = **2,147,483,648 States**.

For a full 2v2 field (4 Pokémon testing spread moves), this bound increases to $24 \times (32,768)^4 \approx$ **$2.76 \times 10^{19}$ States**.

## 2. Limits of the Fixed-Point Accumulator

The engine uses a `fixed_point<27>` data structure to accumulate probability representation.

> [!IMPORTANT]
> The available 27 bits for defining fractional representations is entirely insufficient to support the branch tree bounds generated by 2v2 or 3v3 simulations, rendering the deepest subsets of valid probabilities mathematically equivalent to 0.

### The Math: 
* The fractional baseline representable by 27 bits is roughly $2^{-27}$.
* A move branch hitting a critical hit ($1/16$) at a specific damage interval ($1/16$) yields a target probability of $1/256$, or **$2^{-8}$**.
* Across three targets, evaluating this rare outcome generates an absolute probability branch of $(2^{-8})^3 =$ **$2^{-24}$**.
* By the time a second multi-target move resolves on this environment state, the compounding probability cascades to $(2^{-24})^2 =$ **$2^{-48}$**. 

Under a standard expectiminimax simulation modeling massive branching scenarios, precision tracking strictly demands 128-bit integers (providing ~96 fraction bits for tracking 2v2) or massive-scale custom fixed precision objects (~240 fractional bits for 3v3 tracking).

## 3. Workarounds and Technical Solutions

To safely traverse such an extensive state boundary within limited time/space environments, consider implementing the following algorithmic solutions:

### A. Context-Aware Accuracy Scaling
Modify the `setAccuracy()` evaluation to check context-specific dependencies dynamically. Evaluating 16 damage outcomes is practical against a single target, but a multi-target `setAccuracy(1)` setting (outputting the uniform expected median) reduces branching outcomes per target to **2** (crit / no-crit). This brings multi-move cartesian output down from $32,768$ to **8**!

### B. Beam Search & Remainder Shifting
Aggressively prune and normalize probabilities during traversal:
1. Cap the engine simulation stack limit (e.g. `n = 1000`).
2. Discard environments holding the most improbable occurrences mid-simulation.
3. Sum the leftover states, compute $1.0 / Sum$, scale all remaining probabilities up, and place any integer fixed-operation remainder truncations onto the most probable stack target point to ensure absolute equality to `1.0`.

### C. State "Smearing" (Expected Value Execution)
Forego distinct discrete branching altogether by scaling mechanical properties inside damage formulas. Rather than generating branches applying 150 damage (Crit) and 100 damage (No Crit), map deterministically to the aggregate **$103$ Damage** formula check. Moves will resolve entirely without generating state duplication.

### D. Monte Carlo Tree Search (The Optimal Refactor)
Expectiminimax engines suffer terribly running exhaustive high-dimensional trees. Transitioning the engine away from fractional stack trackers entirely to MCTS (Monte Carlo Tree Search) enables evaluating probability via PRNG logic without requiring mathematical branching tracking. A simulated outcome evaluates precisely **1** deterministic result. Submitting 500 execution requests simulates complex variability perfectly without requiring exact fraction tracking.
